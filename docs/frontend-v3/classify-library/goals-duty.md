# goals-duty.md — classify-library

## 模块定位（一句话）

为 Library 文档列表新增 **"文件类型"维度**的筛选与展示能力，与现有"文档状态"维度正交并存，使用户能在原料仓库视角下快速定位某一类文件。

---

## 一、Design Goals（设计目标）

1. **维度正交**：文件类型筛选与现有的"文档状态"筛选互不耦合，可任意组合（例如"已完成 + PPT + Word"）。
2. **认知一致**：用户在筛选器中看到的"分组"语义稳定，不会因后端枚举新增就破坏现有心智；同时在表格中保留"事实化"的原始扩展名，避免抽象层覆盖具体信息。
3. **改动收敛**：仅在 Library 列表查询路径上扩展一个正交筛选参数；不引入新的领域实体、不修改 Document 的存储结构。
4. **i18n 完备**：所有面向用户的新增文案（分组名、按钮、列名）必须经由 `uiStrings.libraryPage` 同时提供中英双语，不在组件内硬编码字面量。
5. **UI 语言区分语义**：状态（单选互斥）继续走 tab bar；类型（多选可组合）走 Chip 多选条——交互形态的不同直接表达语义上的不同。

---

## 二、Duties（职责）

本批次（classify-library）需完成且仅完成以下职责：

1. **后端：Library 文档列表支持按 `content_type` 多值过滤**
   - `GET /library/documents` 新增可重复的 `content_type` query 参数，接受 `DocumentType` 枚举值。
   - Service 与 Repository 接口同步增加 `content_types: Optional[List[DocumentType]]` 入参，向下传递到 SQL `IN (...)` 条件。
   - `total` 计数与列表查询遵循同一筛选条件。

2. **后端：补齐 `.ppt` 到 `DocumentType.PPTX` 的扩展名映射**
   - 当前 `DocumentType.from_extension` 未收录 `ppt`，会 fallback 到 `TXT`，使存量 `.ppt` 文件分类错误。
   - 在该方法的 mapping 中补 `"ppt": cls.PPTX`，并在 `supported_extensions()` 中加入 `ppt`。

3. **前端：Library 页新增"文件类型"Chip 多选条**
   - 6 个分组：文档(PDF) / Word / 幻灯片 / 表格 / 电子书 / 文本（各自映射到一组 `DocumentType` 值）。
   - 多选、可点选切换、提供"清空全部"按钮。
   - 选中态变化时调用列表接口并把所选分组展开为 `content_type` 多值传给后端。

4. **前端：Library 表格新增"类型"列**
   - 列位置：标题 → **类型** → 状态 → 上传时间 → 操作。
   - 内容：原始扩展名徽章（PDF / DOCX / PPTX / XLSX / CSV / EPUB / MD / TXT），使用现有 `badge` 视觉规范的中性色变体，避免与状态徽章语义色冲突。

5. **前端：i18n 完备**
   - 新增的所有可见字符串（6 个分组名、"文件类型"标签、"清空筛选"、表格"类型"列标题、徽章 tooltip）均加入 `uiStrings.libraryPage`，提供 `zh` 与 `en` 双值。

6. **测试：覆盖新增筛选契约与前端筛选可见性**
   - 后端契约测试覆盖 `content_type` 单值、多值、与 `status` 组合、非法值的响应行为。
   - 前端测试覆盖 chip 选中→请求参数变化、清空全部→请求参数清空、表格"类型"列正确渲染扩展名徽章。

## 三、Non-Duties（非职责，刻意排除）

以下功能虽然相关，但**不在本批次范围内**，刻意延后或交由其他模块负责：

1. **不引入"用户自定义分类 / 标签 / 集合"机制**
   - 自定义归类是 Notebook 的合适职责（用户主动聚合一组文档+对话+笔记），不应混入 Library。Library 的定位是"原料仓库"，只承担"事实派生的筛选"。
   - 若未来需要自定义分类，应当作为独立的 `notebook-collections`（或同类命名）批次立项，包含独立的领域实体、关联表与 CRUD API。

2. **不重构 Library 的分页机制**
   - 当前前端使用 `fetchAll=true` 一次性拉取全部 Library 文档；这是既有问题，但与本批次正交，不在此次修复。新增的 `content_type` 参数同样遵循"后端过滤后再分页"的语义。

3. **不修改 Document 实体的存储结构**
   - `DocumentModel.content_type` 列已存在；本批次不新增列、不做迁移、不引入二级索引。如未来类型筛选成为热点路径再单独评估索引。

4. **不引入文件类型分组的"用户可编辑"能力**
   - 6 个分组的定义在代码中静态声明（数据契约层级），用户不能新增/重命名分组。这与 Non-Duties #1 是一致的——Library 不承担用户层组织职责。

5. **不改变上传流程**
   - 上传时的文件类型识别、转换、入库均沿用现有逻辑。本批次只在已落库的 `content_type` 字段上做筛选与展示。

6. **不引入复杂筛选器扩展（时间范围、文件大小、上传者等）**
   - 本批次只新增"类型"一个维度；其他维度即便有需求也不在本次。Chip 多选条在 UI 上保留扩展空间，但不为此提前抽象。

7. **不增加批量重新分类、批量修正 `content_type` 的工具**
   - `.ppt` 映射修复仅影响新上传或之后被重新处理的文档；存量 `.ppt` 文档的 `content_type` 是否回填修正不在本批次（用户量级小，可手工处理或后续单独脚本，不在本设计范围内）。
